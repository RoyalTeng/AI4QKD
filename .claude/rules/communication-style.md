# 沟通风格规范（项目级）

**用户偏好来源**：2026-04-26 用户明确反馈 —— 不喜欢中英混杂、专有名词堆砌的回答。

**适用范围**：所有 AI 回答（聊天文本、文档解释、决策清单）。
**不适用于**：项目正式文档（`docs/proofs/`、`docs/findings/` 等正式技术稿仍按学术风格写）。

---

## 规则 1：通俗优先

写给用户看的文字，**优先用日常中文表达**。能用一句白话说清楚的，不要堆术语。

**反例（要避免）**：
> 8/11 sub-gap C1(a) PASS / C3 R1 clean，1/11 [RETRACTED] per scope drift smuggling，combined chain 仍 [SYN, conditional on multi-OPEN/residual]

**正例（要这样写）**：
> 11 个小问题里，8 个的引文核对都通过了，第三方代码审查也没问题；有 1 个被发现写错了（自己用了"还没证明"的前提），已经撤掉；剩下 2 个本来就要等你来判断。整条链条目前还只是"草稿级"，不能拿出去引用。

---

## 规则 2：专有名词要随文解释

**第一次出现的专有名词**，括号里给一句中文白话。即使前面已经在 memory 里见过、即使本会话之前提过，**回答的当前段落第一次出现还是要再解释一次**——用户不应该被迫翻找前文。

**例**：
- ❌ "L1.G2 是 path α 最难的 sub-gap"
- ✅ "L1.G2（路径 α 这条证明路线下的第 2 号小问题，叫'嵌入构造'，是 11 个小问题里最难的一个）"

允许的简化：在同一条回答里第二次、第三次再提同一术语，可以不重复解释；但**新一轮回答**重新出现时要再给一遍。

---

## 规则 3：不要中英混杂

**英文术语**只在以下场景保留原文：
- 文献作者姓名（Pirandola, Cui, Khatri-Wilde 等）
- 公式编号（Eq. 11, Theorem 6.3 等）
- 不可翻译的专有概念（QKD, REE, CPTP 等首字母缩写——但这些**必须**配中文解释）

**禁止**的中英混杂模式：
- ❌ "C3 batch round 1 verdict = REJECTED"
- ✅ "第三方代码审查第 1 轮的结论是：拒绝"
- ❌ "需要 user 显式 declare trusted-relay Eve 仅 access H_E"
- ✅ "需要你（用户）明确声明：在'可信中继'这个设定里，窃听者只能接触 H_E 这个空间，不能碰其他的"

**判断标准**：如果一个英文词换成中文不会损失精度，就用中文。

---

## 规则 4：长术语链给一句"译文"

如果某段必须连用 3 个以上术语，回答时**先给一句白话翻译**，再用术语版做技术核对。

**例**：
> 简单说：现在第 3 号小问题（L3.G2）的内容看起来对，但旁边有个"账还没对上"的小问题（Lemma C 的 channel-use counting residual），需要你决定是要单独立项去解决，还是先按"假设对得上"接受。

---

## 规则 5：决策清单要给"最简路径"

列决策给用户时，**最后必给一段"如果你时间紧/不想看完，至少回答这几个就够"**——把阻塞性的、必须用户亲自做的事挑出来。

---

## 规则 6：例外

正式文档（`docs/proofs/*.md`、`docs/findings/*.md`、`RETRACTION.md` 章节正文等）**继续**按学术风格写——这些是给未来评审、外审用的，需要术语精确。

本规则只管**用户对话回答**与**面向用户的小结**。

---

## 规则 7：与 R0.1-R0.3 红线的关系

通俗化**不**等于松动严谨性：

- 即使白话表达，分级标签（[草稿假设]、[文献综合]、[推论]、[定理]）该标还是要标
- 严谨性红线（[CLAUDE.md](../../CLAUDE.md) §0 的 R0.1 / R0.2 / R0.3）的语义不能因为白话而模糊
- 白话只能换"措辞"，不能换"判断"
